## 1. 项目背景与产品理念

### 1.1 一句话定位

TAGO 是一款基于**动态意图匹配**的 AI 原生社交产品。不从「你是谁」开始做社交，而是从「你此刻为什么想认识一个人」开始。

### 1.2 核心主张

- 传统社交依赖年龄、职业、兴趣、MBTI、照片等**静态资料**；但人的社交需求一直在变化。
- TAGO 的核心不是 Profile，而是 **Tag**：用户用一个 Tag 表达当前社交意图，如 `#周末想找个人看展`、`#刚来到上海，想认识一些新朋友`。
- 产品只解决一件事：帮助两个完全陌生的人，从**公共距离**跨越到**社交距离**——即判断「这个人现在值得聊聊吗？」，之后的关系发展交给真实的人。

### 1.3 四个核心机制

| 机制 | 说明 |
| --- | --- |
| Tag + AI 三问 | 发布 Tag 后，AI 动态生成 3 个问题（理解当前状态 / 社交意图 / 互动偏好），用户回答后进入匹配池 |
| 意图成本（Cost of Intent） | 想认识对方必须先回答对方 Tag 的三问，不能直接私聊；对方看完回答后决定是否接受。双方确认后才开放聊天 |
| AI Gift（动态礼物） | AI 结合双方 Tag、聊天内容、互动节点、关系节奏，动态生成「只属于这段关系」的礼物，轻量提示、不强推消费 |
| Gift Wall / 礼物路书 | 每件礼物绑定「一个人 + 一段小故事」，形成关系记忆（Relationship Memory）这一长期情感资产 |

### 1.4 商业化原则

- 基础连接免费；为更快被遇见付费（Tag Spotlight 置顶竞拍，卖的是 Chance｜机会），为更好地表达心意付费（AI Gift，卖的是 Expression｜表达）。
- 礼物红线：不送礼物不影响匹配权重、不换联系方式、不解锁权限、AI 不高频催消费、礼物价值来自寓意而非价格。

## 2. 用户角色与典型场景

### 2.1 用户角色

| 角色 | 描述 |
| --- | --- |
| 游客 | 未登录，可浏览公开 Tag 流（建议只读、不可发起认识），核心行为前引导登录 |
| 普通用户 | 发布 Tag、回应他人三问、发起/接受认识、聊天、收发礼物 |
| 付费用户 | 购买 Tag Spotlight 曝光位、购买 AI Gift |

### 2.2 典型场景（来自产品 PDF 的完整流程，作为端到端验收剧本）

> Avis，25 岁，刚来到杭州。

1. **创建 Tag**：输入 `#刚到杭州，周末想认识一个可以一起逛逛城市的人`。
2. **AI 生成三问**：Q1 相处方式偏好 / Q2 期待长期还是轻松同行 / Q3 一对一还是小组；Avis 作答并发布。
3. **动态匹配**：AI 结合 Tag + 三问 + 城市 + 时间 + 他人正在发生的 Tag，推荐 6 人。其中 Mori 的 Tag 是 `#在杭州生活两年，最近想重新认识这座城市`——意图高度互补（一个想第一次认识杭州，一个想重新认识杭州）。
4. **发起认识**：Avis 点「想认识 TA」，不直接进聊天，而是先回答 Mori 的三问，提交认识申请。
5. **接受认识**：Mori 看到申请人是谁、想因为哪个 Tag 认识自己、三个回答，点击「认识一下」，聊天开放。
6. **开始聊天**：聊天顶部常驻「你们因为两个关于'重新认识杭州'的 Tag 而认识」，双方三问可随时查看，第一句话自带上下文。
7. **AI 识别表达节点**：周末两人一起去了书店，Avis 说「这是我来杭州以后第一次真的觉得自己开始认识这座城市」。AI 轻量生成候选礼物「🗺 城市第一页」（¥9.9），Avis 觉得合适后送出。
8. **进入礼物墙**：Mori 的礼物墙多了一件绑定故事的礼物，长期沉淀为关系记忆。

## 3. 产品信息架构

### 3.1 底部导航（2 个主 Tab + 1 个居中动作）

| Tab | 名称 | 说明 |
| --- | --- | --- |
| 1 | 发现 | Tag 信息流：我当前的 Tag、置顶 Tag、推荐 Tag 列表 |
| — | 发 Tag（居中凸起） | 发布新 Tag 的创作流程（独立页面，非 Tab） |
| 2 | 相遇 | 认识申请 + 聊天列表的聚合入口 |

> 「发 Tag」是高优先级动作，不是可保留页面栈的 Tab；从发布流程返回时，应回到进入前页面。H5 / 小程序 / App 均使用同一套自定义底部导航，避免原生 TabBar 无法稳定还原中间凸起按钮。

### 3.4 核心对象与状态口径

| 对象 | 状态 | 规则 |
| --- | --- | --- |
| Tag | `draft` / `generating` / `active` / `closed` / `expired` / `moderating` / `rejected` | 推荐流只出现 `active`；替换当前 Tag 时，旧 Tag 原子地转为 `closed`，不能短暂同时生效 |
| 认识申请 | `pending` / `accepted` / `declined` / `expired` / `withdrawn` | 只有 `pending` 可接受或拒绝；任何终态都不可再次操作；状态变更由服务端时间与版本号裁决 |
| 会话 | `active` / `blocked` / `closed` | 接受申请后唯一创建；重复接受不得生成重复会话；拉黑后转 `blocked` 并禁发消息 |
| 消息 | `local_sending` / `sent` / `delivered` / `read` / `failed` / `recalled` | `local_sending`、`failed` 是前端展示态，其余以服务端为准；用 `client_msg_id` 幂等 |
| 礼物订单 | `created` / `paying` / `paid` / `failed` / `closed` / `refunding` / `refunded` | 仅服务端支付回调可确认 `paid`；前端支付返回成功不等于最终入账 |

**统一时间口径：** 到期、申请有效期、第 N 天均按服务端时间计算；前端只负责格式化展示。列表项同时携带 `id`、`status`、`updated_at`（必要时增加 `version`），避免轮询与 WebSocket 乱序覆盖新状态。

**关系快照口径：** 申请提交时固化双方 Tag、三问问题与回答快照；后续 Tag 关闭、到期或替换不影响该申请的审核与已建立会话中的“认识缘由”。头像、昵称显示当前资料，但关系卡必须能查看当时快照。

## 4. 功能需求详述

> 优先级定义：**P0** = MVP 必须有；**P1** = MVP 后第一个迭代；**P2** = 验证成立后再做。

### 4.1 账号与基础资料（P0）

| 编号 | 需求 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| FR-1.1 | 手机号验证码登录 | H5 一期主登录方式；小程序二期加微信一键登录 | 验证码 60s 重发；登录态 30 天 |
| FR-1.2 | 基础资料填写 | 昵称（2–12 字）、头像、城市、年龄段。**不做**完整资料页、兴趣标签、人格测试——违背产品理念 | 必填项缺失时不可进入主流程；可随时修改 |
| FR-1.3 | 游客模式 | 可浏览发现页 Tag 流，点击「想认识TA」或发 Tag 时拉起登录 | 未登录任何写操作均被拦截并引导登录 |
| FR-1.4 | 协议与年龄确认 | 首次注册须勾选用户协议、隐私政策，并确认已满 18 周岁；协议版本与同意时间由后端留痕 | 未勾选不可注册；协议更新后按合规要求重新确认 |
| FR-1.5 | 登录安全与退出 | 验证码次数、设备与 IP 风控由后端控制；前端正确展示冷却、超限、账号异常等状态 | 不通过文案泄露账号是否存在；退出后清除本地敏感缓存并断开 WS |

### 4.2 发布 Tag（P0，核心流程）

对应原型图 10。

| 编号 | 需求 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| FR-2.1 | 写 Tag | 单行便签样式输入，固定 `#` 前缀，上限 100 字，实时字数统计；空内容禁止下一步 | 26/100 式计数；超限时输入被截断并提示 |
| FR-2.2 | AI 三问生成 | 提交 Tag 后调用 AI 接口生成 3 个个性化问题；**生成中必须有 Loading、取消与失败重试态** | 3 问与 Tag 语义相关；失败可重试；同一请求重复返回不得覆盖用户已输入的回答 |
| FR-2.3 | 三问作答 | 每问一个输入卡片（黄/蓝/绿三色便签轮换），每题上限 200 字；图 10 底部「换个问题」定义为**重新生成整组三问**，已有回答时须二次确认 | 三题全部作答后才可发布；答案可修改；换题后旧问题与答案不再提交 |
| FR-2.4 | 连接条件 | 有效期（即时 / 本周 / 30 天 / 长期，默认本周）、相遇方式（线上 / 线下 / 都可以）、地区（不限 / 城市选择） | 条件影响匹配与 Tag 生命周期；发布后不可改有效期，可提前关闭 |
| FR-2.5 | Tag 生命周期 | Tag 到期自动下线；同一用户同时仅 1 个生效 Tag，发新 Tag 需确认替换当前 Tag | 到期 Tag 在「我的 Tag」中置灰归档；替换有二次确认；并发发布由服务端保证唯一生效 |
| FR-2.6 | 内容安全 | Tag 与回答提交前过文本安全接口（后端），命中则提示修改 | 违规内容不可发布，且不暴露具体词库 |
| FR-2.7 | 草稿与离开保护 | Tag、回答和连接条件按用户维度本地暂存；离开有未提交修改时提醒 | 登录切换时不得串草稿；发布成功或主动放弃后清理；本地不存审核命中详情 |

### 4.5 认识申请（接收方，P0）

对应原型图 8、12。

| 编号 | 需求 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| FR-5.1 | 申请横幅 | 相遇页顶部「有人想认识你 · N 个新的认识申请」，未读角标 | 数量实时准确（轮询/WebSocket） |
| FR-5.2 | 申请卡片 | 头像、昵称、城市·时间、「TA 想因为 #xx 认识你」、对方申请附言、Q1–Q3 及其回答、「看看TA」「接受认识」「暂时不了」 | 卡片内可直接决策，也可进详情 |
| FR-5.3 | 申请详情 | 双方三问**并排对比**（我的回答 vs TA 的回答，绿/蓝气泡对照），底部「暂时不了」「认识TA」 | 对比数据完整；按钮防连点 |
| FR-5.4 | 接受认识 | 双方建立连接，创建会话，跳转聊天页并自动展示关系上下文卡；接受接口必须幂等 | 聊天页顶部出现「你们因为 #xx 而认识」；重复点击或多端同时接受只产生一个会话 |
| FR-5.5 | 拒绝（暂时不了） | 软拒绝：申请转 `declined` 并归档，不向申请方披露拒绝原因；申请有效期默认 72 小时，到期转 `expired` | 申请方统一看到「本次申请已结束」，不区分拒绝或过期，避免永久“等待回应”与状态悬挂 |
| FR-5.6 | 防骚扰 | 同一用户对同一 Tag 仅 1 次申请机会；被「暂时不了」后 30 天内不可对同一人新 Tag 再申请（P1） | 规则触发时前端给出温和提示 |
| FR-5.7 | 多端与并发状态 | 列表加载后仍可能收到 WS 状态更新；决策失败时按服务端最新状态刷新 | 已被另一端处理的申请不再展示可操作按钮；未读数以服务端快照校准 |

| FR-6.9 | 举报与拉黑 | 聊天页「···」菜单：举报（分类+描述）、拉黑（双向断开连接） | 拉黑后双方列表互不可见，会话关闭 |
| FR-6.10 | 顺序与断线恢复 | 服务端消息携带会话内单调递增 `seq`；重连后按最近 `seq` 增量补拉，WS 仅作实时通知 | 弱网重连后无重复、无缺口、顺序稳定；历史分页与实时消息可正确合并 |
| FR-6.11 | 相遇页搜索与筛选 | 对应图 7 顶部搜索/筛选：搜索昵称、Tag 或消息摘要；筛选未读、含新申请、已收礼等 | 搜索只在本人会话数据内执行；清空条件可恢复完整列表；M1 若不实现则设计稿隐藏图标 |
| FR-6.12 | 聊天内容安全 | 文本/图片消息进入后端内容安全与风控链路；发送方可见审核中、发送失败或已处置状态，接收方不展示未通过内容 | 前端校验不能替代服务端审核；命中时不给出词库细节；举报证据由服务端按合规要求保存 |

### 4.7 AI Gift 动态礼物（P1，商业化核心）

| 编号 | 需求 | 说明 | 验收标准 |
| --- | --- | --- | --- |
| FR-7.1 | 礼物节点提示 | AI 识别到值得表达的节点后，由后端在聊天内下发轻量提示（非弹窗强推），如「昨晚似乎是一次值得记住的聊天」，用户可一键忽略 | 无打扰式呈现；忽略后短期内不再为同一节点提示 |
| FR-7.2 | 候选礼物生成 | 用户点击提示 → 展示 AI 生成的候选礼物：图标 emoji、名称（如「翻到同一页」）、故事文案（结合双方 Tag 与聊天）、寓意一句话、价格 | 文案必须含关系上下文，禁止出现通用模板句 |
| FR-7.3 | 重新生成（P2） | 「再想想别的表达」换一件候选礼物 | 单次节点最多换 3 次 |
| FR-7.4 | 购买与送出 | 确认后创建服务端订单并拉起支付（H5：微信支付/支付宝；小程序：微信支付；App：支付方式须在上架前完成平台合规评估）；服务端支付回调确认后，礼物消息与礼物墙记录原子写入 | 前端支付成功页先显示「结果确认中」并查询订单；失败不生成礼物；重复回调/查询不重复送礼 |
| FR-7.5 | 礼物红线（产品约束） | 不送礼物不影响匹配权重；礼物不解锁任何权限；价格区间建议 ¥3.9–19.9 | 前端不得出现任何「送礼换特权」的 UI 暗示 |

| 可观测性 | 每次请求携带 `request_id`，错误上报包含版本、平台、网络状态与匿名用户标识；线上 source map 私有上传，不随产物公开 |

## 6. 数据埋点与验证指标

MVP 的核心是验证产品 PDF 第 16 页的 8 个假设，前端需支撑如下数据采集：

| 待验证假设 | 对应指标 |
| --- | --- |
| 1. 用户是否愿意用 Tag 表达当前社交意图 | 新用户发 Tag 率、人均 Tag 发布数 |
| 2. Tag + AI 三问是否足以支撑陌生连接 | 三问作答完成率、申请通过率 |
| 3. 先答三问再申请能否提升聊天质量 | 接受率、首次会话消息数、次日回复率 |
| 4. 动态意图匹配 vs 静态资料匹配 | 匹配点击率、连接后 7 日留存对比 |
| 5. 是否愿为 Tag 曝光付费 | Spotlight 购买转化（P2 后观测） |
| 6. AI 能否准确识别表达节点 | 礼物提示的忽略率 vs 查看率 |
| 7. 是否愿为动态礼物付费 | 礼物支付转化率、复购率 |
| 8. 礼物墙是否形成长期情感价值 | 礼物墙回访率、收礼用户次月留存 |

### 6.1 指标口径与最小事件集

- 所有转化率必须同时写清**分母、时间窗、用户去重方式、实验版本**；例如“申请通过率 = 72 小时内被接受的申请数 / 已成功提交的申请数”，拒绝和过期都进入分母。
- P0 最小事件：`discover_view`、`tag_create_start`、`tag_questions_generated`、`tag_publish_success`、`application_start`、`application_submit_success`、`application_resolved`、`conversation_created`、`message_first_sent`、`report_submit`、`block_confirm`。
- P1 增加：`gift_hint_view`、`gift_preview_view`、`gift_order_created`、`gift_payment_confirmed`、`gift_wall_view`。支付转化以服务端确认事件为准，不以前端“支付成功”回调为准。
- 每个事件至少包含 `event_id`、`occurred_at`、`session_id`、`anonymous/user_id`、`app_version`、`platform`、`experiment_ids` 与业务对象 ID；禁止携带 Tag、回答和聊天正文。

## 8. 风险与依赖

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| AI 三问生成时延 | 发布流程中的同步等待会损害转化 | M1 先用骨架屏、取消/重试与超时降级；根据真实 P95 再决定 H5 是否引入流式返回 |
| AI 礼物文案质量 | 文案不佳直接伤害付费意愿 | 前端提供反馈入口（👍/👎），支持「再想想别的表达」 |
